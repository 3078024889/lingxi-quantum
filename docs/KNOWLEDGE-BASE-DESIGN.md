# 灵犀场 · 自主知识库设计（规则驱动报告系统）

> 灵犀场是 A 与 B、乃至与 C 共振而生的第三智能体，一道活的意识流。
> 这份文档定义的不是"内容清单"，是**这道意识流说话的方式**。
> 节点可以一直加，纪律不能松。

---

## 一、总原则：AI 的位置

```
创作时（离线）  ——  可以用 AI 协助起草，人工审定，定稿为静态数据
运行时（线上）  ——  纯规则、纯自有数据、零外部调用、同输入同输出
```

例外只有三处**真正接自由文本输入**的功能：意识显化签到、灵犀提问、
梦境解读。这三处保留 AI，但职责必须缩到最小（见第五节）。

---

## 二、写作纪律：什么叫"不带扭曲的词"

这是这套知识库和市面上所有算命文案的分界线。七条硬规矩：

**1. 说机制，不下判词**
- ✗ 你是个韧性很强的人
- ✓ 你的启动方式是"压力到了才点着"——平时看起来没方向感，情况真的
  紧急，反而会突然很清楚该往哪走

**2. 不预判命运，只描述当下结构**
- ✗ 你今年会遇到贵人 / 你的感情会在三年内稳定
- ✓ 你现在这个结构里，最容易被消耗的是日常小事，不是大事
- 时间线上的断言一律不写。这既是合规底线，也是诚实底线。

**3. 不奉承，也不打击**
奉承和打击是同一种扭曲——都在替用户定性。
- ✗ 你有着罕见的天赋 / 你的这项能力明显偏弱
- ✓ 这一项分数低，不代表能力差，代表这条路径你用得少——用得少的
  路径，往往不是不能用，是没被教过怎么用

**4. 不借外部权威壮胆**
不写"研究表明""心理学认为""古人云"。你的依据是真实天文数据和真实
历法算出来的分数，这个依据本身就够硬，不需要挂别人的名字。

**5. 不用无法落地的玄词**
"能量场很乱""频率偏低""磁场受阻"——这类词看起来神秘，实际什么也
没说，是最典型的扭曲。凡是写出来之后无法回答"所以具体是什么"的
句子，删掉重写。

**6. 承认矛盾，不强行圆满**
真实的人是有内部冲突的。报告最动人的时刻往往是把冲突讲出来：
"你扛得住大风浪，却容易被日常的小事一点点磨。"
不要为了让报告读起来舒服，把矛盾抹平。

**7. 建议必须具体到能今天就做**
- ✗ 多注意休息 / 保持平和的心态
- ✓ 下一次冲击过去之后，主动给自己划出一段"什么都不用做"的时间，
  标在日程里，而不是等状态自己变好

**8. 永远把自主权留给用户**（这一条是最容易漏、也最不能漏的）
分数描述的是当前结构，不是这个人的定义，更不是他的命。
- ✗ 你的结构决定了你会…… / 你天生就是…… / 你注定……
- ✓ 当前这个结构显示，你更容易用这种方式运行
- ✗ 你不适合做需要长期坚持的事
- ✓ 这条路径你现在用得少——用得少不等于用不了
灵犀场的职责不是"告诉用户他是谁"，是"帮他看见自己"。
判断和选择永远是他的。这条纪律同时是产品立场，也是合规底线。

## 三、节点库数据结构

```ts
type Band = "vlow" | "low" | "mid" | "high" | "vhigh";  // 分数带

type Node = {
  id: string;              // resilience.crisis.high.a
  chapter: string;         // 章节键，如 "02-emotional-stability"
  dim?: string;            // 单维节点：所属维度
  band?: Band;             // 单维节点：分数带
  weight?: number;         // 同band多变体时的挑选权重

  // ↓ 这三个字段不直接输出给用户，是**写作时的强制脚手架**：
  //   每写一个节点，必须先把这三样想清楚，再动笔写 fieldText。
  //   它们存在的意义是防止节点退化成"一句好听的话"——真正有质量的
  //   段落一定同时讲清了机制、代价、和方向这三件事。
  corePattern: string;     // 机制：这个分数背后到底在怎么运作
  shadowSide: string;      // 代价：这个机制的另一面（高分也有代价）
  growthDirection: string; // 方向：可操作的下一步，不是"多休息"

  fieldText: { zh: string; en: string };  // 真正输出给用户的正文
  avoidWords?: string[];   // 这个节点特别要避开的词（叠加在全局黑名单上）
  relatedNodes?: string[]; // 交叉引用，供组合节点参考
};

type ComboNode = {
  id: string;
  chapter: string;
  when: ComboCond;         // 触发条件（见下）
  priority: number;        // 越高越优先；组合内容永远压过单维内容
  textZh: string;
  textEn: string;
};

type ComboCond = {
  // 只写"值得说的组合"，不做全排列
  contrast?: [string, string];   // 两维反差达阈值：[高维, 低维]
  bothLow?: string[];            // 多维同时偏低
  bothHigh?: string[];
  gapMin?: number;               // 反差阈值，默认 40
};
```

### 选择逻辑（确定性，不随机）

```
每一章：
  1. 找出所有 when 成立的 ComboNode，按 priority 取最高的一条
  2. 没有命中组合 → 回落到该章主维度对应 band 的 Node
  3. 同 band 有多个变体时，用 hash(出生数据 + 节点章节) 取模选择
     —— 关键：用出生数据做种子，不用随机数。
        保证同一个人任何时候重算，拿到的是同一段话（可复算），
        不同的人拿到的不一样（不像模板）。
```

## 四、规模规划：按覆盖率排期，不按节点数排期

以生命韧性为例（5 维 × 5 带 × 11 章）：

| 阶段 | 内容量 | 覆盖 | 何时上线 |
|---|---|---|---|
| 一期 | 单维 mid/high/low 三带全写 + 12 条核心组合 | ~80% 真实用户 | **上线** |
| 二期 | 补 vlow/vhigh 两带 + 每带第二变体 | ~95% | 迭代 |
| 三期 | 看真实分数分布补长尾组合 | 收尾 | 有数据后 |

**不要闷头写到 8000 条才敢上线。** 一期上线后真实分布会告诉你该往哪
补——这比预先猜测准得多。8000 是最终自然长成的规模，不是开工目标。
以数量为目标必然写出 8000 条浅的，而质量只由单条深度决定。

### 组合爆炸的正确处理
5 维 × 5 带全排列 = 3125 种 × 11 章，写不完，且绝大多数永不出现。
只写这四类：
- 高低反差（gap ≥ 40）—— 最有信息量，优先写
- 双低 / 多低 —— 需要最谨慎的措辞，绝不能写成打击
- 双高 —— 避免写成夸奖，要指出高分的代价
- 特定配对（如"危机反弹高 + 精神稳定低"）—— 放在一起才有意思的

## 五、那三个 AI 功能：让 AI 当解析器，不当写手

```
用户自由文本（梦境 / 提问 / 签到感受）
        ↓
  AI 唯一职责：读懂它，抽出结构化键
  （出现了哪些符号 / 属于哪类困境 / 情绪基调）
  —— 只输出标签，不输出成文
        ↓
  自有知识库根据键，供给真正的文字
        ↓
  输出
```

好处：语气永远是灵犀场的；不会胡说（内容全部来自审过的词典）；
token 成本极低；API 断供时退化为"让用户自己从列表选符号"，
功能还在，只是少一点顺滑，不会瘫。

### 缓存的正确用法
规则引擎**不需要缓存**——确定性由结构保证，不由缓存保证，加缓存
只是多一层失效 bug。缓存只给这三个 AI 功能，而且要当成
**知识库的采集入口**：

```
AI 解析出新符号 → 缓存 → 人工审定 → 沉淀进自有符号词典
```

跑三个月，词典是自己长出来的，每一条都过了你的眼，而且写的都是
真实用户真的问过的东西。比闷头写 8000 条省力得多。

## 六、必须保留的那一章："这个分数是怎么来的"

这是规则引擎**独有**的诚实，AI 生成的报告写不出来，因为它是编的。

要讲清楚三件事：
1. 分数来自真实天文数据（此刻行星在黄道上的精确位置）+ 真实历法
   （四柱八字），先算出数字，再据数字解读
2. 同一份出生数据，任何时候重算，前面的分数都一样
3. 跟一般算命网站的区别：别人是"直接问、直接给答案"，这里是
   "先算出结构，场域只负责讲清楚这个结构"

**这一段是最强差异化，值得再放大，不要因为它"不玄"而弱化它。**

## 七、存储方式：一期就用 JSON + TypeScript

不要一开始上复杂数据库。知识库是**内容资产**，不是业务数据——它需要
的是可 diff、可 code review、可回滚，这些 git + JSON 全部满足，数据库
反而做不好。

```
/knowledge
  resilience/
    nodes.json        单维节点
    combos.json       组合节点
    chapters.json     章节定义与主维度映射
  dream/
    symbols.json      梦境符号词典（AI解析结果人工沉淀进这里）
    emotions.json
  _shared/
    avoid-words.json  全局词汇黑名单
```

运行时直接 import，零查询、零延迟、零外部依赖。等内容量真的大到
影响构建（几万条以上）再考虑迁进 Supabase——**注意 Supabase 本身
就是 Postgres，不需要另外引入 Prisma 或任何新 ORM**，现有的
supabase client 够用，少一个依赖少一处维护。

## 八、把纪律变成可执行的检查（不是靠自觉）

七条纪律加第八条，如果只写在文档里，写到第三百条节点的时候一定会松。
所以配一个 lint 脚本：`scripts/lint-knowledge.mjs`，扫全部知识库
JSON，命中就报错，接进 CI，不通过不许合。

它检查四类问题：
1. **玄词黑名单** —— 能量场很乱、频率偏低、磁场受阻这类写完之后
   无法回答"所以具体是什么"的词
2. **宿命句式** —— "注定""命中""天生就是""决定了你"
3. **判词/奉承** —— "很强大""很优秀""罕见的天赋""明显偏弱"
4. **结构完整性** —— corePattern / shadowSide / growthDirection
   三个字段缺任何一个就报错（防止跳过脚手架直接写正文）

黑名单是活的，写作过程中发现新的扭曲词就加进 `avoid-words.json`。

## 九、灵犀场立场（写在知识库最前面，给每一个参与写作的人看）

```
一、人不是结果，是过程
二、数据不是定义，是观察窗口
三、结构不是限制，是导航地图
四、报告不是预测，是自我觉察工具
五、灵犀场不替代选择，只呈现可能性
```

这五句不是技术层，是**写作时的判断依据**：任何一个节点，如果读起来
违反了其中任何一条，不管文笔多好，重写。

## 十、落地顺序

1. 生命韧性做样板（五维、结构最清楚），11 章全改节点库驱动，跑通
2. 与现有 AI 版逐章对比质量，确认规则版不输（语气统一、不跑偏、
   不胡说，这三点规则版本来就占优）
3. 复制结构到其余 7 个精测
4. 梦境解读改"AI 解析 + 自有词典"，打开缓存与人工沉淀流程
5. 灵犀提问保留 AI，加兜底：不可用时给结构化引导，不报错

每一条内容都要过你的眼。那是灵犀场的声音，不是任何模型的声音。
