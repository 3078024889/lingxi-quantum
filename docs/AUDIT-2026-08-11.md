# Lingxi Field Engineering Audit Snapshot

Date: 2026-08-11
Scope: local repository, report generation, PDF export, authentication boundaries, performance readiness
Status: first pass; production infrastructure and Supabase policies still require external verification

## Fixed in this pass

### Critical: relationship report IDOR and entitlement bypass

The relationship generation route had replaced the authenticated server client with a module-level privileged client and removed owner and paid-entitlement checks. A caller who knew a submission ID could request another user's paid report.

Resolution:

- restore authenticated user lookup;
- verify submission ownership;
- verify an active relationship-resonance entitlement;
- use the privileged client only after authorization;
- constrain report updates by submission ID and owner ID;
- stop returning internal exception details.

### High: broken relationship API contract and language cache

The route returned report while the client required fullReport. It also stored Chinese text in full_report_en.

Resolution:

- restore fullReport, resonance, and vectors response fields;
- generate and cache Chinese and English independently;
- upgrade short legacy reports to the 11-section structure;
- preserve valid 11-section snapshots unless explicit regeneration is requested.

### High: PDF innerHTML injection

PDF prose was escaped, but cover titles and chapter titles were inserted into innerHTML without escaping. Relationship cover titles can contain user-supplied names.

Resolution:

- escape ampersand, angle brackets, and all cover/chapter title strings before HTML insertion.

### High: resilience route retained unreachable model implementation

Life Resilience already used the local knowledge planner at runtime, but the route still contained a complete Zhipu endpoint, credential path, retry loop, and prompt implementation. That made the zero-token boundary easy to regress and obscured the true architecture.

Resolution:

- physically remove the endpoint, credential, prompt, retry, and fetch implementation;
- reduce the route duration ceiling from 300 to 30 seconds;
- require the new 12-section snapshot before accepting cached reports;
- constrain cache updates by submission owner and surface persistence failures;
- add an executable route audit that fails if deterministic products regain fetch or model markers.

### High: copied save-route error disclosure

Daily Tide, Life Oracle, Resilience, Romance, and Life Mirror save routes returned raw Supabase codes, messages, table names, and deployment instructions to end users. The same copied routes also accepted birth years through 2100.

Resolution:

- keep complete database errors in server logs only;
- return stable generic client errors;
- replace 2100 with the runtime current year;
- keep table provisioning details out of public responses.

### Medium: report cache writes lacked defense-in-depth owner constraints

Life Map, Life Oracle, Romance, Daily Tide, and Life Mirror checked ownership before generation but cached reports by submission ID alone and ignored persistence failures.

Resolution:

- constrain updates by submission ID and owner ID;
- check database update results;
- return 503 when a completed report cannot be persisted.
### Medium: hard-coded maximum birth year

Seven client and server validators rejected years after 2026.

Resolution:

- use the runtime current year in Life Map, Relationship, Resilience, Romance, and Life Mirror validation paths.

### Repository hygiene

The repository had no .gitignore and exposed build/dependency directories as untracked content.

Resolution:

- add standard ignores for node_modules, Next.js output, environment files, Vercel state, build metadata, and debug logs.

## Open high-priority findings

### Mobile report asset weight

Most report background PNG files are approximately 2.2-2.9 MB each and a report can reference 12 images. A single WeChat reading session can therefore approach 25-35 MB before charts and application JavaScript. This conflicts with fast mobile opening and 20,000-user burst traffic even when a CDN is present.

Required:

- produce AVIF/WebP screen derivatives;
- retain high-resolution originals only for export when necessary;
- preload cover only, lazy-load later chapters;
- measure on constrained China mobile networks;
- set immutable cache headers and verify CDN hit ratio.

### Client bundle size

The production build reports roughly 459 KB first-load JavaScript on the home page and up to 654 KB on Life Map. This is too high for the intended three-second mobile entrance.

Required:

- isolate Three.js behind dynamic loading and viewport activation;
- keep report readers free of WebGL dependencies;
- measure parsed/executed JavaScript, not only transfer size;
- define page budgets and fail CI when exceeded.

### Missing Content Security Policy

Security headers include HSTS, frame protection, content-type protection, referrer policy, and permissions policy, but no CSP. Inline styles, JSON-LD, external fonts, payments, Supabase, and WebGL assets require a staged CSP rollout.

Required:

- deploy Content-Security-Policy-Report-Only first;
- collect violations;
- move toward nonces or hashes for executable inline content;
- explicitly allow only required payment, Supabase, font, and media origins.

### Review-mode architecture

REVIEW_MODE is currently a source-code boolean that bypasses authentication and payment checks across many server routes when enabled. It is false now, but enabling it in a public production deployment would expose all paid reports.

Required:

- remove global bypass from production builds;
- use a separate protected preview deployment;
- require an allowlisted reviewer account and server-side claim;
- add a build assertion that production cannot enable review mode.

### Capacity is unverified

No repository evidence demonstrates 20,000 concurrent-user capacity. Deterministic prose removes model bottlenecks but database auth, entitlement checks, serverless quotas, image delivery, and client PDF work remain.

Acceptance gates:

- k6 or equivalent staged test at 1k, 5k, 10k, and 20k virtual users;
- separate cache-hit, first-generation, payment-return, and PDF scenarios;
- database connection and rate-limit metrics;
- p50, p95, p99 latency and error rates;
- idempotency checks during retry storms;
- documented Vercel, Supabase, and CDN quotas.

## 部署前安全加固（本轮）

已完成：

- 生产构建硬性禁用付费审核绕过，审核模式仅允许开发环境显式开启。
- 微信 OAuth 回跳仅允许灵犀场同源 `/checkout`，使用 256 位随机 state 与 HttpOnly、SameSite Cookie 绑定。
- PayPal 回跳绑定真实 provider token；PayPal 与微信回调均核对渠道、金额、币种。
- 订单履约迁移为 Supabase 单事务 RPC，锁定订单后原子写入权益与 paid 状态，避免重复延期和部分写入。
- 支付平台回调在权益写入失败时返回非 2xx，以保留平台重试能力。
- 八张付费报告表撤销浏览器增删改权限，仅允许 authenticated 读取本人记录；写入统一经过已鉴权 API。
- 限流表、缓存表与内部 RPC 收紧为 service_role，RLS 归属列和支付回调查找列补充索引。
- 增加 CSP Report-Only、COOP、Origin-Agent-Cluster 和 DNS 预取控制；CSP 先观察再转强制。
- 新增 `npm run audit:security`，覆盖审核绕过、OAuth、支付、原子履约、RPC 权限、CSP 和错误泄露。

### 必须按顺序部署

1. 先在 Supabase SQL Editor 执行更新后的 `supabase/schema.sql`，确认 `fulfill_paid_order` 创建成功且仅 `service_role` 可执行。
2. 再部署 Next.js 应用。若顺序相反，支付确认会暂时返回“权益开通待重试”，不会错误标记为已开通。
3. 使用 PayPal Sandbox 与微信支付测试商户各完成一次真实的“下单、付款、异步回调、重复回调、报告解锁”全链路测试。
4. 观察 CSP Report-Only 浏览器告警，收敛外部域名白名单后再切换为强制 CSP。
5. 在独立预发布环境完成阶梯压测；当前生产构建成功不等于已证明 2 万并发。

尚未完成且不能伪称完成：真实支付沙箱回调、线上 Supabase SQL 执行、CSP 告警采集、CDN 命中率验证、2 万并发压测。
