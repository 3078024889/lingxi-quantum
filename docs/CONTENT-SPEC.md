# 灵犀场知识库 · 内容填充规范

把内容写成这个格式放进 JSON，**不需要改任何代码**，报告立刻生效。

---

## 一、文件位置

```
knowledge/<产品>/
  chapters.json   章节定义（已建好，不用动）
  nodes.json      单维节点 ← 主要工作在这里
  combos.json     交叉节点（两维关系）
  tails.json      章末灵犀校验
  states.json     状态层（暂时留空）
```

产品目录名：`resilience` `romance` `wealth` `qian` `tarot`
`relationship` `life-map` `daily`

---

## 二、单维节点（nodes.json）

每个产品需要 **5 维 × 5 分数带 = 25 条**（第 2–6 章），
后 5 章（07–11）复用维度，另需 25 条，共 **50 条**。

```json
{
  "nodes": [
    {
      "id": "w.02-insight.high",
      "chapter": "02-insight",
      "dim": "insight",
      "band": "high",
      "weight": 1,

      "corePattern": "能提前看到趋势，判断快且多数时候准",
      "shadowSide": "看得太早，别人还不理解，容易孤立地承担风险",
      "growthDirection": "把判断写下来并标日期，让它可被验证",

      "fieldText": {
        "zh": "正文 200–300 字……",
        "en": "English body text……"
      }
    }
  ]
}
```

**字段说明**

| 字段 | 作用 | 在报告里怎么出现 |
|---|---|---|
| `corePattern` | 这一章最凝练的一句判断 | **❖ 开头的核心洞察句**，用户翻开第一眼看到 |
| `shadowSide` | 这个机制的代价 | 【要留意的】 |
| `growthDirection` | 可操作的下一步 | 【下一步】 |
| `fieldText` | 正文 | 章节主体 |

三个短字段各写 **15–30 字**，正文 **200–300 字**。

**`band` 五档**：`vlow`(0–24) `low`(25–44) `mid`(45–64) `high`(65–84) `vhigh`(85–100)

## 三、章末灵犀校验（tails.json）

这是让报告"眼前一亮"的关键，**每维每带一条，25 条**。

```json
{
  "tails": [
    {
      "id": "tail.02-insight.high",
      "chapter": "02-insight",
      "dim": "insight",
      "band": "high",
      "fieldText": {
        "zh": "灵犀校验：你能比多数人早看到东西，而说出来的时候常没人接。如果是这样……",
        "en": "Field check: ……"
      }
    }
  ]
}
```

**写作要求（这三条不能松）**

1. **必须可证伪** — 说一句对某些人明确是错的话。
   研究显示，让报告显得"通用"的正是模糊、对冲、全是好话。
   说对了用户会有"它怎么知道"的反应；说错了用户也知道
   这份报告在认真判断，两种都比"模糊的正确"有价值。
2. **描述行为与场景，不描述人格**
   ✗ 你很敏感 → ✓ 别人还在说，你已经在想怎么回应
3. **禁用「有时候 / 可能 / 往往」** — 那正是通用文案的标志

## 四、交叉节点（combos.json）

讲两个维度**放在一起说明了什么**——这是"说的就是我"的真正来源，
因为它是这个人独有的组合，不是分类标签。每产品 5–8 条即可。

```json
{
  "combos": [
    {
      "id": "w.x.insight-vs-build",
      "chapter": "03-build",
      "when": { "contrast": ["insight", "build"], "gapMin": 35 },
      "priority": 25,
      "fieldText": { "zh": "……", "en": "……" }
    }
  ]
}
```

**触发条件三种**
- `{"contrast": ["高维","低维"], "gapMin": 35}` 落差达标时触发
- `{"bothLow": ["维A","维B"]}` 两维都在低带
- `{"bothHigh": ["维A","维B"]}` 两维都在高带
- `{}` 空条件 = 兜底，priority 设低（如 5）

`priority` 高于单维节点时会**覆盖**该章内容而非并列。
第 1 章（总览）必须靠 combos 覆盖，因为它 `dim=null`。

---

## 五、八条写作纪律（lint 会强制检查）

1. **说机制，不下判词** — ✗你很有韧性 ✓你的启动方式是压力到了才点着
2. **不预判命运** — 时间线上的断言一律不写
3. **不奉承也不打击** — 两者是同一种扭曲，都在替用户定性
4. **不借外部权威** — 不写"研究表明""心理学认为"
5. **不用无法落地的玄词** — 写完之后答不出"所以具体是什么"的，删掉
6. **承认矛盾，不强行圆满** — 报告最动人的时刻常是把冲突讲出来
7. **建议具体到今天就能做** — ✗多注意休息 ✓下次冲击过后主动划出一段什么都不做的时间
8. **永远把自主权留给用户** — ✗你的结构决定了你会 ✓当前结构显示你更容易这样运行

**低分节点尤其要守第三条**：先说明"这是当前状态不是上限"，
再给一件门槛低到不需要意志力的具体动作。

---

## 六、写完怎么验证

```bash
node scripts/lint-knowledge.mjs
```

会检查：玄词黑名单、宿命句式、判词奉承、空泛建议、
三个短字段是否缺失、**每章五个分数带是否都有节点**（缺了报告会空白）。

不通过就修，通过了直接生效——不需要重启、不需要改代码。
