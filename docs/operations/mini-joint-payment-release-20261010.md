# 小程序三种收款方式一起上线

用户已明确要求：工具按次虚拟支付、10/88/666/888/自定义充值、人民币余额支付按次工具一起开放。分开上线建议已被用户修改，本次按一起上线准备。

## 已完成与已验证

- 原生付款页增加余额支付及原生充值入口；余额支付仅使用已验证小程序会话的用户身份，不接受客户端指定用户。
- 复用现有 `pay_tool_quote_with_sasi_balance` 原子事务；人民币报价不使用美元余额。
- 原生页拦截重复点击、已经完成的支付和外部付款结果未确认时的支付方式切换。
- 隔离 PostgreSQL 执行现有生产 SQL：重复充值不重复入账，重复余额支付不重复扣款，只创建一份订单与权限，交付失败回滚扣款。没有操作真实订单或余额；未验证多连接竞争及真实微信退款。
- 原生余额支付、充值客户端、虚拟支付签名及小程序结构检查通过。

## 自动审批与替代实现

自动审批拒绝新增退款资金来源表、全局账本触发器、自动退款扣款及权限撤销的迁移。拒绝原因是全局副作用与退款逻辑尚未充分验证。该迁移未创建、未执行，生产资金结构不变。

随后实现限定到具体微信虚拟支付订单的替代迁移 `20261010143000_mini_order_scoped_refund.sql`，无全局账本触发器、不更换扣费函数、不追扣其他充值或旧钱包。真实 PostgreSQL 隔离执行通过后已成功部署；匿名和登录用户均无退款 RPC 执行权限，只有服务端可执行。全额工具退款撤销该订单权益，部分或共享用量退款暂停对应任务并记录人工核对；不冻结整个账户。历史充值来源不猜测，转人工核对。

新增服务端微信退款通知查询：核对原订单、退款单、生产环境、金额与累计退款差额，失败退款只记录不扣款。后台显示微信退款、已扣回余额和需核对金额，并提供未完成通知的重试入口。

## 退款边界

1. 新充值需要逐笔追溯来源，退款仅扣回退款订单尚未消费的人民币本金。
2. 微信确认退款后，重复通知只处理累计退款差额；先退款后到账的迟到通知不能重新增加余额或恢复权限。
3. 已消费金额、历史来源不明确金额和部分工具退款进入管理员核对记录，不认定为自动追偿欠款。
4. 不追扣其他订单充值、美元或旧钱包资金；不因单笔退款冻结整个账户。
5. 工具未消费权益的撤销需要对应订单及用量的明确核算，已交付结果保留历史记录。
6. 当前处理微信已确认的虚拟支付退款，不新增自动发起虚拟支付退款接口。小程序退款需在微信虚拟支付后台按原单处理，再核对到账与余额；不能使用旧普通支付退款接口处理虚拟支付充值。
