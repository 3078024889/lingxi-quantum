# 全球 SIAI 目录扩容架构审计（2026-11-05）

## 审计范围与可核查事实

- 公开首页目录：**32 个精选产品 + 30 个官方资料来源预览 = 62 个产品记录**，不是 62 家经过实际支付验证的企业，也不代表 62 家互不关联的公司。
- 分批候选库 B001–B010：**100 个产品记录，归入 88 个发布方分组**。30 个 B001–B003 产品作为来源预览出现在公开目录；B004–B010 的 70 个仍不公开。所有 100 条候选的 `reviewed` 和 `publishApproved` 均为 false。
- 已有七项字段总计 `100×7=700` 项；可追溯官网来源观察 **304**，明确缺失 **396**。这只是来源观察完整度，不是账号注册/付款/功能验收。
- 支付方式统计仅使用有来源的付款记录，并保留地区限制。一个厂商同时提供银行卡、支付宝和 PayPal 可重复出现于不同支付筛选；不能把支付标签相加作为厂商总数。
- 新的认领申请写入 Supabase `ai_market_vendor_submissions`；数据库上次核查共有 0 申请。仅当前已核准的管理员能够读取并审批。认证并不等于自动更改产品排序或公开发布。
- 所有数据源的更新时间、价格单位、地区、支付渠道、公司法人/集团关系均应分别验证；不要以集团旗下其他产品的条款推断一个产品的结算条件。

## 已发现并修复的数据或技术缺陷

1. Vidu 发布方为中文“生数科技”，早期 ASCII-only slug 产生 `publisherGroupId:"-"`；改为稳定英文厂商 ID `shengshu-technology`。
2. Amazon Bedrock、AWS Q Developer 和 AWS SageMaker 都属于同一 AWS 发布方体系，历史分组分别写成 `amazon` 与 `aws`；当前统一 `amazon`，保留独立产品 ID 与不同的计费模型。
3. 原公开目录写死“32/62”，以后每次发布会反复改代码。新增逐项 ID 的 `directory-publication-manifest.json`，每次公开修改必须显式列出产品 ID。预览仍保留 `source_preview` 状态。
4. 原管理员候选页面分别 import 五个批次，新增一批就要修改页面；改为单个 `market-private-intake-index.ts` 负责 10 批数据、6 份观察包和后续新批次入口，后台自动显示三种审核阶段。
5. 原管理员厂商申请接口单次最多读取 100 条。现提供上限明确、权限隔离的分页，确保增长后仍能访问历史申请和未审核数量。
6. 后台从只显示平台名称，升级为显示七项事实的证据来源、核验日期、字段完整度和独立产品/发布方分组。
7. 新增严格批次审计：唯一产品 ID、非空发布方 ID、无孤儿候选、HTTPS 来源、站内公开白名单隔离、相同公司名称不分裂多个组、可复现的来源完整度统计。

## 厂商身份：品牌、合同主体、集团不是同一字段

- Cursor 的 SpaceX 集团归属，以 Cursor 2026-08-14 官方公告为依据；合同运营主体 Anysphere 另外记录。
- Leonardo.Ai 与 Canva 的集团关系，以 Canva 官网发布的收购公告为依据。Leonardo 产品支付条件不能直接复用 Canva 支付条件。
- Tabnine 归入 Tricentis，以 Tabnine 官方产品页为依据；仍须核对实际订单主体。
- Lightricks 官网页标注 LTX 业务正在拆分，不能在拆分完成之前将新法人当成已成立事实。该关系单列 `restructuring_review`。
- 字节跳动官方明确火山引擎为其企业服务业务。产品与发布方分组必须保持两级主键，不以营销名称推定公司注册年份。

可审计关系保存在 `publisher-parent-evidence.json`，注明日期、来源及不可自动批准状态。

## 开源方案对比与选择

| 参考实现 | 有价值的成熟做法 | 当前决定 |
| --- | --- | --- |
| [TanStack Table（MIT）](https://github.com/TanStack/table) | Faceting、排序、服务端行模型与虚拟化 | 沿用已有紧凑表格交互；先复用多维筛选思想，不因 100 项数据引入重构 |
| [Typesense（GPL-3.0）](https://github.com/typesense/typesense) | 错别字容忍、同义词、分组、全文索引 | 需要数千家及更高搜索负载再评估；当前不增加长期搜索服务器成本 |
| [Meilisearch](https://github.com/meilisearch/meilisearch) | 搜索词容错、索引管理、Facet | 先评估索引数据质量与当前许可证；不复制不明许可代码 |
| [OpenMetadata](https://github.com/open-metadata/OpenMetadata) | 数据血缘、来源、所有权、数据质量及审计链 | 借鉴字段级来源和审核状态设计，不部署重型元数据平台 |
| [Supabase 安全文档](https://supabase.com/docs/guides/database/postgres/row-level-security) | RLS、服务端密钥隔离、最小权限 | 认领资料独立私有、人工授权，严格限制站长 API 的读写 |

**未拷贝任何第三方项目的未核实代码**。先用现有 Next.js＋GitHub＋Supabase 架构修复真正的问题，避免额外服务器、授权和升级成本。
