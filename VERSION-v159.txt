【一、生命向量引擎 + 矛盾检测算法——真正的架构落地，不再只是提示词】
═══════════════════════════════════
lib/life-vector.ts（新增）

这是这次真正新增的一层代码逻辑，不是又调了一遍AI的说话方式：

- computeLifeVector()：把星盘+八字的原始数据（太阳月亮五大行星的元素、
  日主五行、命局五行分布、年月时三柱的十神），用固定的映射规则，转成
  十个带权重的数值维度（自由需求/稳定需求/创造倾向/秩序纪律/风险偏好/
  情感深度/内省倾向/社交驱动/野心驱动/适应弹性，各0-100分）。这一步是
  纯代码计算，同样的出生数据永远算出同样的结果，不依赖AI、不会因为
  AI状态不同而每次给出不一样的判断。

- findConflictsWithFallback()：在算出的十个维度里，扫描六组"语义上真实
  对立"的维度对（比如"自由需求 vs 稳定需求"），找出两个维度都是高分、
  又足够接近的组合，判定为这个人身上真实存在的"内在矛盾"。这就是GPT
  建议里说的"矛盾检测引擎"，这次是真的用代码实现的，不是靠AI自己在
  一堆命理名词里"悟"出来。

- wealthArchetypes()：判断这个人最接近五种财富来源类型（创造型/资源型/
  专业型/机会型/经营型）里的哪一到两种。

app/api/lifemap/generate-full/route.ts

- 这套引擎的输出，现在直接注入进给AI的提示词里，格式是"【生命向量
  引擎 · 已计算完成，直接使用】"——AI不再负责"发现"矛盾在哪，只负责
  "讲述"已经算出来的矛盾具体怎么体现，这是这次架构升级最核心的一句话
  总结：判断的活，从AI手里，挪到了确定性代码手里。
- 第8章财富分析，也从"AI自己判断类型"，改成了"直接使用引擎算出的
  类型判断"。

老实话：这是一套v1版本的规则引擎，映射规则是我根据命理学常见的元素/
十神对应关系人工编写的，不是跑过大规模数据训练出来的模型，覆盖面也
不是穷尽所有命理学细节——但这已经是"确定性代码判断矛盾在哪"和"让AI
自己从原始数据里猜矛盾在哪"这两件事之间，真正的架构级差异，不是原地
调了一遍话术。以后要把这套规则表做得更细、更准，可以持续往里加规则、
调权重，不需要再改动上层的报告生成逻辑，这是这套架构设计带来的好处。

【二、全新产品：关系共振图谱（合婚/合伙/合财富通用），$9.9】
═══════════════════════════════════
新增页面：/relationship（两人信息录入）、/relationship/full（结果展示）
新增接口：/api/relationship/save、/api/relationship/generate-full
新增数据表：relationship_submissions

- 复用了你反复强调的"五套系统不能丢"这个前提——两个人各自完整跑一遍
  跟生命图谱同一套计算引擎（西方占星+八字，是同一个函数
  computeLifeMapFacts，不是另外发明一套算法），再用上面第一部分那套
  生命向量引擎，各自算出一份生命向量。
- 核心创新在"关系共振引擎"（lib/life-vector.ts 的 compareLifeVectors）：
  拿两份生命向量互相比较，找出三种关系：
  · 共鸣点——两人在同一维度上都是高分（共享的驱动力）
  · 互补点——一人这一端高、另一人恰好补对立那端高（天然分工）
  · 摩擦点——两人在同一种倾向上都很高、缺另一种力量平衡（容易叠加放大）
  这三种关系，直接决定了AI报告要写"吸引来源""关系动力""冲突地图"
  这几章的具体内容，不是空泛地讲"合不合"。
- 报告结构：吸引来源 / 关系动力 / 冲突地图 / 长期潜力 / 成长方向，
  五章。提示词里明确禁止"合不合""匹配度85%"这类算命/营销式表达。
- 支持三种关系类型（亲密关系/商业合伙/其他），同一套引擎，AI提示词
  里区分类型来写，不需要三套不同算法。
- 定价$9.9，永久解锁，解锁一次之后可以反复测不同的两个人组合，不用
  每次重新付款——这一点在代码里做了处理：提交前会先检查有没有解锁过，
  已解锁的话直接跳过付款，不会误收第二次钱。
- 已经接入了搜索框（搜"关系共振图谱"能直接搜到）。

【部署前必做】
═══════════════════════════════════
在 Supabase 的 SQL Editor 里手动跑这一条（建新表）：

create table if not exists public.relationship_submissions (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users(id) on delete cascade not null,
  name_a text not null,
  name_b text not null,
  birth_input_a jsonb not null,
  birth_input_b jsonb not null,
  facts_a jsonb not null,
  facts_b jsonb not null,
  relationship_type text default 'romantic',
  full_report text,
  full_report_en text,
  created_at timestamptz default now()
);
alter table public.relationship_submissions enable row level security;
drop policy if exists "own relationship submissions" on public.relationship_submissions;
create policy "own relationship submissions" on public.relationship_submissions
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);

（完整的这段SQL，也已经写进了 supabase/schema.sql 文件里，如果你更
习惯直接跑整份 schema.sql，也可以，里面这段是新加的，其余部分都是
之前已经跑过的，重复跑不会报错。）
